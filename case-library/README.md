# 线下服务案例维护

本批目标50篇；只把完成原笔记与账号核验、互动至少一项≥50的记录写入 `batches/`。当前数量与缺口由 `status.json` 生成，不与旧通用案例混算。

## 更新流程

1. 正常登录灵犀／小红书，列表初筛，原文及账号核验。登录失效、验证码、访问限制时停止该批采集，不绕过。
2. 保存为 `batches/YYYY-MM-DD.json`，结构 `{schemaVersion:1, records:[...]}`。字段参考首批；不得存密码、分享令牌、评论者个人资料或长篇原文。正文只保留必要的原创摘要与限制。
3. 记录ID用原笔记ID；账号与活动分别关联。不同采集日期的同ID记录作为修订，同批重复报错。粉丝约数明确说明；转发、核销等未获取写null，不补零。
4. 执行 `node case-library/validate.cjs --build`，再执行 `node tests/check.cjs` 与 `node tests/service.cjs`。失败不发布。
5. 审查数据与文案，提交同一个版本，推送既有仓库，验证正式页面数量、筛选、来源与导出。

每天10篇是目标，不是必须凑满。建议配额：发帖3、引流裂变3、背书2、首次体验1、复访1。每周集中判断是否新增做法或更新模板，不每天自动生成10套近似模板。

已在当前聊天配置每日09:30北京时间的本地定时任务（应用任务ID 10）。需要电脑开机、桌面应用运行及有效浏览器登录；首次无人值守执行待验证，`unattendedRunVerified:false`。脚本只校验和构建，采集由定时聊天按正常浏览器操作完成，未建立独立云端采集服务。成功发布、失败或需要人工处理时通知；同一阻塞无变化时保持安静。

先将首批15篇扩充至50篇，之后持续每日增量。首批品牌最多5篇、账号最多3篇；规模增长后分别不超过总数10%和5%（向上取整，保留首批上限下限）。同日重跑先比对已完成批次，不重复发布。若来源可用但合格记录不足10篇，可发布已核验部分并说明缺口；来源异常或校验失败不发布。

## 证据标准

- A：活动规则、相关内容和可追溯到店结果。
- B：活动规则与互动核验，尚无核销结果。
- C：仅内容和互动证据；不认定为自发分享或高转化活动。

跨行业只迁移方法，不移植价格、频次、资质或服务效果。维护视频未逐帧核验时，只标记其选题方法。用户发帖案例须区分合作关系；无活动关联，不填造关联ID。
